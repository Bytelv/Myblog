给博客接上 Steam：一个实时同步的游戏库页面

前阵子给博客加了装备图鉴，做完就想着再搞一个游戏库页面：把 Steam 库里的游戏、
各自的游玩时长，还有「现在正在玩什么」都显示出来。

游戏库页面（/games/）

头像、昵称、「最近两周」和全库时长都是从 Steam 拉的，打开页面时会自动刷新一次。

为什么不能在前端直接调 Steam 接口

想法很直接：页面上 fetch 一下 Steam 的接口不就行了？但有两个拦路虎：

两个硬障碍

CORS：api.steampowered.com 不返回 Access-Control-Allow-Origin，浏览器直接请求会被拦下来；密钥：Steam Web API 要带 API key，而它是账号凭证，不能写进前端代码——静态博客的 JS 人人可见。

所以中间必须有个”代理”：它拿着 key 去问 Steam，把结果用带 CORS 的形式吐给页面。
所以我的方案是用Cloudflare Worker——免费额度足够，几十行代码，还顺手能加缓存。

整体架构：快照 + 实时

两条通路，各管一件事：

通路什么时候更新作用
构建时快照每次部署（hexo generate）把游戏库渲染成静态 HTML——没 JS 也能看，SEO 也友好，数据是”最近一次构建时”的
客户端实时刷新每次打开页面向 Worker 要一次实时数据，只更新「正在玩」、时长、最近两周；失败就静默保持快照

这样分工的好处是：Worker 挂了、网络抽风、公司网络拦了，页面都还是完整的（只是数字旧一点）；
反过来，Worker 正常时「正在玩」这类信息是分钟级的。

部署指南

第一步：拿 Steam API key，并把隐私放开

  1. 打开 https://steamcommunity.com/dev/apikey（要登录 Steam），域名随便填 localhost 就行，拿到 key；
  2. 个人资料 → 编辑 → 隐私设置，把「游戏详情」设为公开。

第 2 步很容易漏：它不是公开的话，接口返回的 games 是空数组（接口本身还是 200，不会报错），
页面就会显示”库为空”。我第一次就是这么被自己绕进去的。

第二步：部署 Worker

Worker 我单独放了一个仓库：**Bytelv/steam-worker**。

第三步：绑自己的域名（重要）

别用默认的

*.workers.dev workers.dev 在国内被 DNS 污染，无法访问

正确做法是绑自己的域名：Cloudflare Dashboard → Workers & Pages → 选中你的 Worker →
Settings → Domains & Routes → Add → Custom Domain，填一个子域名。

第五步：抓一份构建时快照

Hexo 是静态站点，页面内容得在构建时就存在——不然没有 JS 的访客看到的是空白。
抓取脚本干的事就是调 Steam 这几个接口，揉成一份 JSON：

接口拿什么
ISteamUser/ResolveVanityURL个性网址 → steamID64（steamid 填了就不需要）
ISteamUser/GetPlayerSummaries昵称、头像、在线状态、当前在玩的游戏（gameextrainfo + gameid）
IPlayerService/GetOwnedGames整个库 + 每款总时长（要加 include_played_free_games=1）
IPlayerService/GetRecentlyPlayedGames最近两周（playtime_2weeks 比前者更全）

三个一定踩得到的点

一、封面图要加 no-lazy：Stellar 的懒加载会把 src 换成占位图、再靠外部 CDN 脚本还原，而封面是跨域外链，实测整页封面会空白；二、改完 _data/*.yml 必须 hexo clean：页面源文件没变，Hexo 会复用 db.json 里的旧渲染结果，症状是”改了数据页面纹丝不动”；三、脚本报 fetch failed（cause: UNABLE_TO_GET_ISSUER_CERT_LOCALLY）是 Node 用自带 CA 库、不认本机代理的证书，改用 curl 请求即可。

小结

技术栈就是三样：Steam Web API 提供数据、Cloudflare Worker 做代理和缓存、Hexo 标签 + 一小段前端 JS 负责呈现。
总共不到 400 行，效果是打开博客的「游戏库」页面就能看到我今天在玩什么。
